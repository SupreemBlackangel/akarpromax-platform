# Email DNS Readiness (SPF / DKIM / DMARC)

Purpose: document exactly what DNS/email-authentication configuration the
**future** SMTP provider + sending domain require, what must be verified, and
how AkarProMax will confirm readiness. **No DNS values are fabricated here**
because no provider/domain has been selected yet (requires Product Owner
approval and domain/DNS changes).

Current status: `EMAIL READY = NO` — `EMAIL_TRANSPORT` unset → `console`,
`productionCapable = false` (`npm run email:check` confirms).

## Sending identity (target)

- From name: `AkarProMax` (`MAIL_FROM_NAME`)
- From address: configured domain mailbox, e.g. `no-reply@<sending-domain>`
  (`MAIL_FROM_ADDRESS`) — must be a real mailbox/domain; do NOT reuse
  `no-reply@akarpromax.om` unless that domain is actually configured.
- Reply-To: support/contact mailbox where applicable (`MAIL_REPLY_TO`).

## What must be configured (after provider + domain selection)

### 1. SPF (Sender Policy Framework)

- A TXT record authorizing ONLY the selected provider's relays for the sending
  domain:
  `v=spf1 <provider-mechanisms> -all`
- Requirements:
  - The exact SPF string comes from the chosen provider's docs — do not invent.
  - No conflicting SPF records for the same domain (only one `v=spf1` TXT).
  - The `MAIL_FROM_ADDRESS` domain must be the SPF-covered domain.

### 2. DKIM (DomainKeys Identified Mail)

- A TXT record publishing the provider's DKIM selector key for the sending
  domain, e.g. `selector._domainkey.<domain> TXT v=DKIM1; k=rsa; p=<pubkey>`.
- Requirements:
  - Selector + public key exactly as generated by the provider.
  - Enable DKIM signing in the provider dashboard (provider signs outbound).
  - Signing domain must match the `MAIL_FROM_ADDRESS` domain (alignment).

### 3. DMARC (Domain-based Message Authentication)

- A TXT record at `_dmarc.<domain>`:
  `v=DMARC1; p=none; rua=mailto:<reporting>; ruf=mailto:<forensics>`
  start with `p=none`, then tighten after monitoring.
- Requirements:
  - Reporting addresses must exist and be monitored.
  - SPF+DKIM alignment must satisfy DMARC at the intended policy level.

## What must be verified

| Check | Method |
|---|---|
| SPF record present + no multiple SPF | `nslookup -type=TXT <domain>` / provider tool |
| DKIM selector resolves | `nslookup -type=TXT <selector>._domainkey.<domain>` |
| DMARC record present | `nslookup -type=TXT _dmarc.<domain>` |
| SMTP auth works | `npm run email:check` → `transport=smtp, configured=true, productionCapable=true` |
| Provider accepts message | live send (SMTP `250` / messageId) |
| **Actual inbox arrival** | register → open verification email → verify → login → welcome email (SMTP `250` alone is NOT delivery) |
| SPF/DKIM/DMARC pass on received mail | inspect raw headers of the received message (Authentication-Results) |

## How AkarProMax confirms readiness

1. `EMAIL_TRANSPORT=smtp` + SMTP/MAIL env fully set (see
   `STAGING_ENVIRONMENT_MATRIX.md`).
2. `npm run email:check` reports `configured=true`, `productionCapable=true`.
3. `GET /api/health/ready` returns `200` with
   `email.productionCapable=true` (503 otherwise in production).
4. **Real inbox journey** executed on the sending address:
   - register a fresh UAT account →
   - verification email actually arrives in the inbox (not spam) →
   - verification succeeds from the received link/OTP →
   - login succeeds →
   - welcome email actually arrives.
5. Raw headers of the received messages show
   `spf=pass`, `dkim=pass`, `dmarc=pass` (or pass-aligned) with
   `Authentication-Results` from the receiving provider.

## Decision gate

- If SPF/DKIM/DMARC (or provider equivalent) are NOT configured and verified:
  **`EMAIL READY = NO`** and readiness stays 503.
- Only after all of the above is `EMAIL READY = YES` and the email blocker clears.
